# Alt+C4 confirmed brief

This brief consolidates the user's requirements for an external implementation agent. The accompanying phase plan is `../plans/2026-11-16-altc4-phases.md`. Writing the plan does not authorize implementation of the game in the planning turn.

## Goal and deadline

Build CodeBox Alt+C4 (Boom Banana), a cooperative code-puzzle bomb game for a school demonstration by **December 1, 2026**. The owner of the original eight tasks is JEFF MARQUEZ. Role Assignment's earlier In Progress label did not represent implementation work; all eight tasks start unimplemented.

The planned architecture uses one shared backend for several Tauri desktop hosts, room isolation, and two browser players per Alt+C4 room. Inspect the repository before implementation; folder names and retained dependencies do not prove working features.

## Confirmed experience

- Three devices: a separate Tauri desktop host, a Spec Holder browser, and a Programmer browser. The desktop controls configuration and game start and displays a shared bomb perspective.
- Random initial assignment of Spec Holder and Programmer. Their information stays private to their roles; server-only answers stay on the backend.
- The Spec Holder sees instructions, a brief, checklist, timer, and chances. The Programmer sees bomb panels, constrained code editing, timer, and chances. Surrounding code is locked.
- Offer Java, C++ (CPP), and Python. The implementation agent authors starter puzzles, briefs/checklists, validation material, reference solutions, and original-bug explanations.
- A bomb has several panels. All panels must be solved before time expires. The desktop host configures the duration before play.
- The countdown continues during answer checking. Each checked incorrect submission removes exactly one of three chances. Zero time or zero chances detonates the bomb; all panels solved in time defuses it.
- A player or host disconnect pauses the round and allows reconnection. Preserve progress, including editable work.
- Results explain the original bugs. Then return to the lobby for optional role/configuration changes and another game when ready. Automatic role swapping and automatic next-round progression are superseded.
- The user rejects unintelligible code. Use clear names, focused modules, explicit state transitions, and straightforward control flow. Follow existing conventions and preserve unrelated work.

## Visual direction and frontend scope

The selected direction is **playful retro bomb workshop, using pixel art**. Exact palette, fonts, pixel density, asset dimensions, and detailed treatments need visual review. Proposed directions include a workbench bomb for the host, a repair console for the Programmer, and a field manual for the Spec Holder. Code and instructional text must remain readable on intended devices.

Design and implement the host bomb view, both private player interfaces, role presentation, feedback, pause/reconnection, results, and replay transitions. Include mockups, reusable controls, assets, and interaction states in the work, with real backend integration.

Another programmer owns the finished lobby. Build a replaceable, functional placeholder for room creation/joining, participants, settings, roles, readiness, start, and replay. Agree its state/action/navigation contract with the other programmer. The supplied lobby image is contextual reference, not an instruction to implement that finished design.

## Desired features and unsettled decisions

- Configurable panel count, if feasible; several panels per bomb remain required.
- A host bomb preview highlighting the Programmer's active panel is desired. A basic shared bomb view remains required.
- In-Game Text Chat was originally listed as MVP. The user now questions its need because players are co-located. Deferral is recommended, not approved cancellation. It is an optional phase pending a decision.
- Proposed: one shared pool of three chances across the whole bomb. Confirm this interpretation before implementing chance consumption.
- Choose a checking approach suitable for constrained edits in all three languages. Explain accepted syntax, valid equivalent solutions, and limitations. Do not misrepresent string equality as general behavior checking or run untrusted submissions directly in the main server process.
- Set explicit duration/panel-count bounds, reconnect grace and abandonment policy, resume behavior, validation time limits, and ordering rules for pending checks during pause/expiry. These defaults are not user-approved yet.
- Developer hours and budget are unknown. Assess capacity and prefer existing tools. Identify feasibility issues without silently dropping a language or other confirmed requirement.
