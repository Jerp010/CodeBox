# Alt+C4 stack recommendation and planning audit

This document applies to Alt+C4's new gameplay interfaces, game rules, and minimum integration adapters. It does not request a rewrite of CodeBox's existing menus, other games, or the finished lobby owned by another programmer.

**Decision status:** Tailwind CSS is the user's confirmed styling choice. React, TypeScript, CodeMirror, the proposed checking approach, and storage/testing choices below are recommendations for Phase 1 to adopt and make concrete. No dependencies or product code were changed by this planning update.

## Recommended stack

| Area | Recommendation | Reason and boundary |
| --- | --- | --- |
| New Alt+C4 frontend | React + TypeScript, built with Vite | Separate components for the host bomb, each role, panels, and results; typed public messages and props make the game flow explicit. Mount only the Alt+C4 screen root in the existing host. |
| Styling | Tailwind CSS 4 with shared theme variables and small custom CSS rules | The confirmed choice. Keep the reviewed pixel-art palette, spacing, fonts, and status treatments consistent across all Alt+C4 views. Tailwind styles the interface; sprite artwork is a separate asset deliverable. |
| Desktop integration | Existing Tauri 2 host with a mount/unmount adapter | Keep the desktop shell and teammate's lobby separate from React's game root. The lobby hands room/session context to the game and receives a return-to-lobby callback. |
| Code editor | CodeMirror 6, with Java/C++/Python language packages | Use it for the allowed editable sections and show surrounding code as locked context. Editor language support provides editing/highlighting, not compilation or correctness checking. Revalidate edits on the server. |
| Local interface state | React hooks and a small reducer; Context only if needed | Keep panel selection and unsent edits local. Server state owns roles, time, chances, panel completion, and outcomes. Avoid adding a separate global-state package until there is a demonstrated need. |
| Alt+C4 server rules | TypeScript game module on Node.js 24 LTS, loaded by the shared backend | Keep game logic separate from Express/WebSocket connection plumbing. Compile server code to JavaScript compatible with the backend's existing CommonJS entry; do not require migration of unrelated JavaScript. |
| HTTP and real-time integration | Existing Express 5 and ws 8 backend; native browser WebSocket clients | Serve the player build and route game messages through the shared server. Build explicit identity, heartbeat, reconnect, privacy, and round-revision rules; the transport alone does not supply those game behaviors. |
| Round storage and content | In-memory rooms; versioned server-only puzzle definitions | Adequate proposed scope for transient demo rounds and reconnecting to a running server. Backend restart would require a new room; durable restart recovery would be an added requirement. Do not expose answer definitions through client imports/static directories. |
| Artwork and motion | 2D PNG sprites/sheets with CSS transitions or short frame animations | Fits the selected pixel-art workshop theme and HTML-based editor/manual interfaces. Keep a consistent pixel scale; actual code/instructions stay readable. A full game engine is not needed for the proposed interactions. |
| Verification | TypeScript checks, Node's built-in test runner for compiled game rules, and Playwright for browser flows | Type-check new frontend/server code, test the state machine/checker, and exercise multiple isolated users. Retain a real native-Tauri host plus two-device rehearsal. |

Java, C++, and Python are the selectable **puzzle languages**. They are separate from the TypeScript implementation language of the game.

## Constrained submission checking recommendation

For the deadline, prefer a small set of authored repair puzzles with explicit editable fields/sections and per-puzzle validators. Examples include correcting a comparison, a constant, or a bounded expression. Define supported syntax for each language variant and make the edit limits visible in the UI.

Parse each edit as data within that puzzle's documented grammar. Apply it to trusted, authored validation logic and check the required behavior with representative fixtures. Cover equivalent accepted edits, incorrect edits, unsupported syntax, and language-specific semantics. Avoid a custom general-purpose interpreter and avoid evaluating submitted source in the main server.

This recommendation does not promise arbitrary Java/C++/Python compilation or acceptance of every valid full-language solution. Actual compiler execution would require a separately isolated runner, toolchains, resource limits, and another integration/test boundary. Phase 1 must record this product trade-off and demonstrate examples before puzzle implementation. If it fails to satisfy the desired puzzles, revise the checking plan explicitly.

Distinguish malformed transport input, unsupported edits, incorrect supported solutions, and internal checker failures. Set their chance-consumption rules explicitly; infrastructure failures must not be silently treated as an incorrect player solution.

## Integration checks required before implementation expands

1. Mount/unmount a small Alt+C4 React screen inside the current host and mount a private view in the browser app. Prove cleanup, leaving/re-entering, and preservation of existing host behavior.
2. Establish one consistent React dependency resolution for both consumers of the game code. Resolve the game's external source imports deliberately; do not duplicate React runtimes or create a broad monorepo rewrite for this feature.
3. Separate frontend TypeScript/TSX bundling from server TypeScript compilation. Define the CommonJS adapter and build order. Add an explicit type-check command: a Vite build alone is not a type check.
4. Configure Tailwind source detection for Alt+C4/shared frontend files outside each app directory. Use complete class names for variants, and prove production CSS includes the game styles in both host and player builds.
5. Keep server-only puzzle material out of both frontend dependency graphs and static-serving paths. Limit development file access to intended public source paths.
6. Wrap CodeMirror with explicit setup/update/cleanup. Timer messages and React re-renders must not reset editor content, selection, focus, or undo history. Check paste and edits at locked boundaries.
7. Use the same shared backend endpoint for player HTTP assets and WebSocket upgrades where practical. Document host endpoint configuration and secure WebSocket selection for an HTTPS demo endpoint. Do not replace the shared backend with one backend per desktop.
8. Keep the lobby contract independent of React. The placeholder and teammate's final lobby must use the same room/configuration/readiness/start/return boundary.

## Final planning audit, November 16, 2026

This is a requirements/compatibility review, not a claim that the game is implemented.

| Check | Result |
| --- | --- |
| Ownership and scope | Covered: new Alt+C4 screens/rules and minimum adapters; teammate owns finished lobby; placeholder remains functional and replaceable. |
| Visual and frontend scope | Covered: pixel-art workshop direction, host bomb, both private roles, editor, results, feedback, pause/reconnect, and reviewable mockups. Tailwind is confirmed. |
| Original tasks | All eight retain explicit phase/status mapping. Chat remains optional pending the user's decision. |
| Three languages and editing | Required in the plan; the proposed bounded checker must demonstrate real authored behavior for all three. General compiler execution is not assumed. |
| Round behavior | Covered: configurable duration, multiple panels, all-panel success, three chances, timer during checking, and exactly-once terminal outcomes. Chance-pool scope and rejection policy remain Phase 1 decisions. |
| Recovery and replay | Covered: disconnect pause, reconnection, original-bug results, lobby reconfiguration, and replay with changed roles. Grace/abandonment/resume defaults remain Phase 1 decisions. |
| Current local baseline | Node v24.19.0 observed. Host lockfile resolves Vite 8.3.6 and Tailwind 4.3.4. Existing host production build passed. This does not verify the proposed React/editor/server modules. |
| Runtime compatibility follow-up | Existing root engine declaration is Node >=20, while the locked host Vite requires ^20.19.0 or >=22.12.0. Use a documented supported Node 24 LTS environment for Alt+C4; align relevant setup metadata during implementation. No runtime upgrade was performed here. |
| Shared-source/build integration | Added explicit gates for React mounting/resolution, TypeScript server output, Tailwind source detection, and private data exclusion. These gates are not yet executed. |
| Phase commits | Preserved: local commits on ALTC4-jeff after checks, with actual hash and original-task status reports. Unrelated edits must stay outside those commits. |
| Deadline | December 1, 2026 retained, with proposed November 29-30 rehearsal buffer. Delivery feasibility still depends on capacity and Phase 1's checking/design decisions. |

**Readiness:** Enough information to begin Phase 1. Reviewed mockups, exact interfaces/defaults, integration proof, and checker examples are deliverables of Phase 1; they are not already completed.
